# 03: 完成 PRD 草稿、评审与批准基线

**What to build:** 让已排期的主需求可以生成一个可开发、可验收的 PRD。产品人员完成 grilling 和自审后提交评审；需求负责人必须单独确认批准。批准时系统锁定 PRD 内容基线并生成可验证的 hash，建立后续开发门禁所需的关联。

**Blocked by:** 02: 完成需求对齐与人工排期

**Status:** ready-for-agent

- [ ] 只有 `PLANNED` 主需求可以创建正式 PRD；一个 PRD 只有一个主需求并覆盖一个功能，相关需求只能作为引用。
- [ ] PRD 保存模块、功能、场景、目标版本、主需求、版本、状态和人员关联。
- [ ] PRD 包含背景目标、范围、现状与变化、场景、AC、非功能需求、数据需求、依赖风险和待确认问题。
- [ ] 场景数量超过 8 个时被拒绝或要求拆分；每个场景至少有一条可测试的 Given/When/Then AC。
- [ ] 新功能缺少功能现状时明确记录“新功能，无现状”，不会因此阻塞创建。
- [ ] 自审能报告章节缺失、范围问题、不可测试 AC、模糊词、术语冲突和跨文档冲突。
- [ ] 提交评审和批准是两个独立确认点；身份和职责不匹配时状态不改变。
- [ ] 需求负责人批准后 PRD 进入 `APPROVED`，并对正文、锁定范围 metadata 和存在的测试用例按相对路径及 UTF-8 字节生成 SHA-256 hash。
- [ ] 评审记录、状态历史和追加记录不会无故改变正文 hash；非法状态跳转和批准前置条件被拒绝。
- [ ] CLI 黑盒测试覆盖未排期创建、场景/AC 校验、提交评审、错误身份、合法批准和 hash 稳定性。
