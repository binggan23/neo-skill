# Neo Skill P0 最小研发闭环

Status: resolved

## Problem Statement

团队已经确定了 Neo Skill P0 的需求、可行性边界和高层架构，但仓库目前还没有可直接交给实现 Agent 的 feature spec。没有这份 spec，后续实现容易出现以下问题：

- Skill 自己维护状态、hash 或审批，导致 AI 交互和确定性规则分裂；
- 需求、PRD、Spec、验证和验收之间缺少稳定的关联；
- AI 可能在没有人工确认的情况下排期、批准 PRD 或判定验收通过；
- 文件写入失败、并发修改或进程中断后，项目可能留下半完成状态；
- 只有文档规则，没有可验证的 CLI 外部行为和违规路径测试；
- P0 范围与后续完整产品研发流程混在一起，导致实现膨胀。

从用户角度看，团队需要一个以自然语言 Skill 为入口、以本地文件为持久化边界、以 `flow-core` CLI 为确定性内核的研发闭环：需求经过 grilling 和人工排期后才能进入 PRD；批准后的 PRD 才能驱动开发；开发必须留下可追溯验证证据；最终由需求负责人进行人工验收，收尾同步成功后需求才完成。

## Solution

实现 Neo Skill P0 最小研发闭环，包含标准 Skill、随 Skill 分发的 `flow-core` CLI、声明式规则与模板，以及项目初始化后保存的项目规则基线。

Skill 负责自然语言理解、事实检索、grilling、候选文档生成和人工确认提示。`flow-core` 负责编号、项目骨架、状态机、hash、开发门禁、结构检查、索引、锁、事务和结构化结果。人工仍然负责排期、PRD 批准和验收通过；CLI 只校验申报身份与职责映射，不实现真实身份认证。

P0 主链路为：需求草稿 → grilling → 需求负责人排期 → PRD 草稿与自审 → 提交评审 → 需求负责人批准并锁定 hash → 绑定 PRD 开发 → Spec/Plan/Tasks/代码/测试 → 验证报告 → 人工验收 → 功能现状、主需求、场景和索引收尾同步。

实现必须以 CLI 的外部行为作为最高测试 seam。自动化测试在隔离临时项目中启动 CLI，观察退出码、结构化结果和文件状态；Claude Code 安装与端到端主链路作为同一 workspace seam 的验收试点，不绑定尚不存在的内部模块。

## User Stories

1. 作为项目负责人，我想通过标准的 Skill 安装方式安装 Neo Skill，使我可以在不依赖开发机源码路径的情况下使用流程能力。
2. 作为项目负责人，我想按官方升级命令升级 Skill，使我不需要维护自定义升级器。
3. 作为项目负责人，我想运行环境诊断命令检查 Python、Node.js、Skill 资源和 `flow-core`，使我能在开始工作前知道缺少什么。
4. 作为项目负责人，我想在诊断失败时看到明确的修复提示，使我可以自行修复环境，而不让工具静默安装全局软件或修改用户配置。
5. 作为项目负责人，我想让 Skill 包自带 CLI、声明式规则和模板，使安装后的项目不依赖当前源码仓库。
6. 作为项目负责人，我想在空项目中初始化完整项目骨架，使所有 P0 产物都有明确的位置。
7. 作为项目负责人，我想让初始化同时创建尚未实现阶段所需的目录骨架，使后续阶段不会因为目录缺失而改变约定。
8. 作为项目负责人，我想在初始化时显式裁剪允许省略的非核心目录，使小项目可以降低维护成本。
9. 作为项目负责人，我想让核心项目管理、需求、PRD 状态与门禁、人工验收能力不可被裁剪，使 P0 主链路始终完整。
10. 作为项目负责人，我想让初始化只创建必要模板而不伪造调研结论、用户数据或业务决策，使项目不会把空白内容误认为事实。
11. 作为项目负责人，我想在已有项目中初始化时保留已有 README、AGENTS、业务文档和代码，使工具不会破坏现有工作。
12. 作为项目负责人，我想在初始化发现文件冲突时先看到变更计划，使我可以在写入前作出决定。
13. 作为项目负责人，我想让受管理的项目约定只更新 Neo Skill 自己的区块，使其他团队约定保持原样。
14. 作为项目负责人，我想重复执行初始化而不重复创建或覆盖已满足的内容，使初始化具备幂等性。
15. 作为项目负责人，我想收集并预览团队摘要，使我可以确认需求负责人和项目负责人配置是否正确。
16. 作为项目负责人，我想在确认团队摘要后才生成团队配置，使未确认的信息不会成为流程事实。
17. 作为需求负责人，我想在团队配置缺失或职责映射无效时被阻止排期和批准，使流程不会记录无法追溯的人工决策。
18. 作为项目负责人，我想获得项目约束的默认模板，使首次正式开发前可以补齐技术、安全、测试和架构约束。
19. 作为项目负责人，我想明确确认项目约束后才允许正式开发，使开发门禁有可检查的前置条件。
20. 作为需求提出者，我想用自然语言创建一个可保存进展的 `NEW` 需求草稿，使我可以分阶段补充信息。

25. 作为需求提出者，我想让系统在没有人工确认时不删除或合并需求，使原始需求记录不会被 AI 擅自改变。

32. 作为需求提出者，我想让 AI 把可查证事实和需要我决定的事项分开，使我不必承担查询项目事实的工作。

109. 作为 Skill 开发者，我想获得稳定的 `success`、`artifacts`、`errors` 和 `next_actions` JSON 结果，使 Skill 可以可靠解释成功、失败和下一步。
110. 作为 CI 维护者，我想命令失败返回非零退出码，使脚本可以阻止错误继续传播。
111. 作为 CLI 使用者，我想人工决策命令强制要求 `--actor` 和显式确认参数，使 CLI 不会默认代替人确认。
112. 作为人工 CLI 使用者，我想直接使用 CLI 完成排期、批准和验收，并获得与 Agent 流程相同的校验，使人工不依赖某个 Agent 才能完成流程。
113. 作为项目负责人，我想系统不自动执行 Git commit、merge 或 push，使版本控制决策仍由团队掌握。
114. 作为安全负责人，我想日志、错误和 CI 输出不包含凭据，使流程工具不会泄露敏感信息。
115. 作为数据负责人，我想系统不主动上传项目文件或依赖独立后端，使本地文件驱动的边界清晰。
116. 作为 Claude Code 用户，我想在隔离环境中安装并发现标准 Skill，使 P0 的目标 Agent 可以完成真实试点。
117. 作为试点负责人，我想从需求到验收完整运行一条真实小项目主链路，使可行性不只停留在单元测试。
118. 作为试点负责人，我想隔离试点不修改现有全局配置、凭据或项目，使验证不会污染开发环境。
119. 作为项目负责人，我想在大约 1,000 条需求或 200 个 PRD 的数据集上完成常规 lint、索引和状态查询，使文件驱动方案可以支持常规项目规模。
120. 作为项目负责人，我想单次状态变更在规定时间内完成，使人工确认不会因确定性操作而明显变慢。
121. 作为审计人员，我想编号只增不复用、废弃对象保留编号和历史，使历史引用不会因为删除或重用而失效。
122. 作为项目负责人，我想 slug 创建后保持不变，使跨阶段路径和关联不会随名称修改而断裂。

## Implementation Decisions

- **交付范围**：实现 P0 的 `flow-core`、`project`、`requirements`、`prd`、`dev` 和 `acceptance` 能力；完整 `flow`、`discovery`、`definition`、`release`、`design`、`growth` 不属于本 spec。
- **架构分工**：Skill 处理自然语言、事实检索、grilling、文档候选内容和确认提示；`flow-core` 处理确定性校验、状态变更、受控写入和结构化结果；AI 不直接承担排期、批准或验收决定。
- **规则单一来源**：安装资源作为发布源，项目初始化后保存自己的项目规则基线；运行时优先使用项目基线，升级只补齐缺失内容或在确认后更新已有内容。
- **CLI 命令契约**：提供稳定的 `init`、`doctor`、`req`、`prd`、`dev`、`acceptance`、`lint`、`index` 和 `recover` 命令组。内部模块可以调整，但 Skill、CI 和人工使用只依赖命令参数与结果契约。
- **人工确认契约**：排期、提交评审、PRD 批准和验收等人工决策要求显式 `--actor` 与确认参数；命令核对团队配置中的职责映射，记录人员、时间、对象、决定和相关 hash 或版本。
- **身份边界**：团队配置只做职责匹配和审计记录，不实现登录、真实身份认证、电子签名或权限系统。
- **输出契约**：每个 CLI 命令都支持人类可读输出和 `--json`。结构化结果至少包含 `success`、`artifacts`、`errors` 和 `next_actions`；错误至少包含错误码、原因、对象和建议下一步。失败使用非零退出码。
- **正式产物格式**：需求、PRD、Spec、Plan、Tasks、验证和验收正文使用 Markdown；metadata 和项目配置使用 YAML；CLI 机器接口使用 JSON；原始测试输出按原始命令格式保存，并额外记录退出码和环境。
- **项目初始化**：初始化创建完整原始项目骨架和必要模板，但不伪造业务内容；允许显式裁剪非核心目录；已有业务文件默认不覆盖；冲突先展示计划；重复执行保持幂等。
- **需求对象**：需求必须具备稳定 ID、slug、模块、分类、来源、状态、目标版本和 PRD 关联；编号只增不复用，slug 创建后不变，废弃对象保留历史。
- **需求状态**：需求按 `NEW`、`TRIAGED`、`PLANNED`、`IN_PRD`、`DONE` 以及受控的延期或拒绝旁支推进。`NEW` 到 `TRIAGED` 需要 grilling 共识确认，`TRIAGED` 到 `PLANNED` 需要需求负责人明确同意并确认目标版本。
- **排期边界**：P0 在 `requirements` 中补齐排期确认，不实现完整 `release`。拒绝排期保持 `TRIAGED`；同意但缺版本时继续询问；只有职责匹配且明确确认后才能进入 `PLANNED`。
- **PRD 对象**：一个 PRD 只有一个主需求并覆盖一个功能，相关需求只能作为引用。PRD metadata 保存模块、功能、场景、主需求、目标版本、版本、状态、人员、hash 和历史。
- **PRD 内容约束**：PRD 包含背景目标、范围、现状与变化、场景、AC、非功能需求、数据需求、依赖风险和待确认问题；场景上限为 8；每个场景至少一条 Given/When/Then AC；新功能无现状时显式标注。
- **PRD 状态**：PRD 使用 `DRAFT`、`IN_REVIEW`、`APPROVED`、`DEVELOPING`、`READY_FOR_ACCEPTANCE` 和 `ACCEPTED` 等状态，并保留受控的变更、拒绝和替代历史。提交评审与批准是两个独立人工确认点。
- **PRD 基线**：批准时对 PRD 正文、锁定范围 metadata 字段和存在的测试用例按相对路径及 UTF-8 字节计算 SHA-256。评审记录、状态历史和 CR 不参与正文 hash。
- **CR 机制**：批准后的锁定内容必须通过 CR 修改。CR 记录原因、变更内容、对 Spec/Tasks/测试/设计/版本的影响、版本变化和审批信息；开发中的 CR 使旧基线失效并要求重新评审和批准。
- **开发门禁**：正式开发必须显式绑定 PRD，并检查 PRD 存在、状态允许、批准记录有效、hash 一致、项目约束已确认、引用关系正确。门禁失败不得生成 Spec、Plan、Tasks 或修改正式代码。
- **开发产物**：门禁通过后建立与同一 PRD 绑定的 Spec、Plan、Tasks 和 Verification。开发开始时 PRD 进入 `DEVELOPING`，适用验证全部通过后才可进入 `READY_FOR_ACCEPTANCE`。
- **范围控制**：AI 和 CLI 必须检查 Spec、Tasks 与代码变更是否超出 PRD。发现需求不明确或范围疑似扩大时停止相关开发，要求 CR 或人工澄清，不自动修改 PRD。
- **验证证据**：验证报告按 AC 关联测试结果，并保存原始输出、退出码和执行环境。未执行、阻塞或失败的验证不能标记为通过；不适用必须记录理由。
- **失败修复限制**：测试失败允许 AI 修复，但默认最多连续三轮，项目约束可以调整；禁止删除用例、降低断言、跳过测试或修改 AC 伪造通过。
- **验收对象**：验收产物包含 Demo 材料、按 AC 生成的 checklist 和验收报告。每项 AC 必须记录通过、不通过或阻塞及证据；AI 可以建议结论但不能确认通过。
- **验收门槛**：只有全部 AC 通过且需求负责人明确确认，PRD 才能从 `READY_FOR_ACCEPTANCE` 转为 `ACCEPTED`。有条件通过、不通过或阻塞不能进入 `ACCEPTED`。
- **验收版本**：提交验收时记录 PRD hash、Git commit 或非 Git 项目的源代码/测试内容摘要、验证报告摘要和 checklist 关联。PRD、验收范围内代码或验证证据变化会使当前提交或验收结论失效。
- **收尾事务**：验收通过后以事务同步功能现状、主需求、场景状态和索引。全部同步完成后主需求才进入 `DONE`；部分失败保留人工结论并显示“已确认通过，收尾未完成”。
- **并发锁**：按需求或 PRD 对象建立锁；跨对象操作按稳定顺序获取锁。残留锁由 `doctor` 报告，不自动抢占或删除；显式恢复前必须确认持有进程已结束。
- **原子写入**：单文件更新通过临时文件、刷新、关闭和原子替换完成；替换失败不得改变正式文件或业务状态。
- **多文件事务**：跨文件操作保存目标文件、原基线、暂存内容、操作顺序和状态，状态为 `PREPARED`、`COMMITTING` 或 `COMMITTED`。`recover` 只能在重新获取锁并验证原基线后继续，不能静默覆盖新修改。
- **索引生成**：`flow-core` 独占 backlog、feature map 和 PRD index 的受管理区块。生成前检查人工修改；确认后只替换受管理区块，区块外内容原样保留；索引失败不改变业务状态。
- **结构检查**：`lint` 检查必需文件、目录与 ID 一致性、孤儿 Spec、失效引用、hash 和基线失效、验收收尾以及索引一致性。
- **Git 边界**：系统只读取和记录 Git 版本，不自动 commit、merge 或 push。非 Git 项目使用内容摘要建立版本关联。
- **兼容性承诺**：`flow-core`、声明式规则、模板、Git/CI 能力 Agent 无关；标准 Skill 面向支持 Agent Skills 规范的 Agent；P0 只对 Claude Code 做隔离端到端认证，不宣称其他 Agent 已兼容。
- **安全与数据边界**：取消 Agent 专属 Hook，不建设独立后端、账号、登录、权限或电子签名；系统不主动上传项目文件，不保存凭据，且日志、错误和 CI 输出不得包含凭据。
- **性能目标**：在约 1,000 条需求或 200 个 PRD 的数据集上，常规 lint、索引和状态查询在 10 秒内完成；单次状态变更在 2 秒内完成，不计 AI 生成和项目测试时间。
- **语言与编码**：Skill 默认中文交互并允许切换语言；目录名、ID、slug 和状态值使用英文；正文使用 UTF-8 并支持中文。
- **实现取舍**：优先使用 Python 3.11+ 标准库，仅引入必要且锁定版本的 YAML 解析依赖；不建设数据库或服务端状态存储。

## Testing Decisions

- **唯一自动化测试 seam**：测试通过 CLI 进程边界操作隔离临时 workspace，只断言外部可见行为：退出码、标准输出、标准错误、`--json` 结果、创建或修改的项目文件、metadata 状态、历史、hash、锁、事务和索引。测试不依赖内部 Python 模块名称或调用顺序。
- **测试质量标准**：好测试应能从用户和 CI 使用者角度证明命令是否允许合法操作、拒绝非法操作、失败时是否无副作用、恢复后是否一致、审计信息是否完整。测试不验证提示词措辞或内部函数实现细节，除非该内容已经成为 CLI 外部契约。
- **测试环境**：每个测试使用独立临时 workspace，预置最小项目、团队配置、项目约束、需求、PRD 或代码版本；测试结束后不修改当前仓库、全局 Skill、凭据或用户配置。
- **CLI 基础契约测试**：覆盖人类输出、`--json` 输出、成功与失败退出码、错误码、对象信息和下一步建议；验证失败不会改变业务状态或留下半写入正式产物。
- **环境与安装测试**：覆盖诊断命令的版本检查、资源检查、缺失资源提示、安装目录相对路径调用和标准 Skill 安装后的资源可发现性。
- **初始化测试**：覆盖空项目创建完整骨架、显式裁剪、重复执行幂等、已有文件不覆盖、冲突计划、受管理约定区块和不伪造业务内容。
- **编号与需求测试**：覆盖编号递增、不复用、slug 稳定、草稿可恢复、需求字段完整、分类、模块、优先级理由、关联提示和无确认不删除/合并。
- **需求状态测试**：覆盖 grilling 确认、拒绝排期、缺少版本、职责不匹配、正确排期、非法跳转、历史追加和人工决定记录。
- **PRD 测试**：覆盖未排期禁止创建、主需求约束、场景上限、AC 完整性、新功能无现状、提交评审与批准分离、职责核对和批准 hash。
- **hash 与 CR 测试**：覆盖正文、锁定范围 metadata 和测试用例的变化检测；评审记录、状态历史和 CR 追加不误触发；批准后直接修改被识别；CR 重新批准生成新版本和新 hash。
- **开发门禁测试**：覆盖未绑定、PRD 不存在、DRAFT、hash 失效、状态不允许、constitution 未确认、引用不匹配、越界范围和门禁失败无正式写入。
- **验证测试**：覆盖 AC 与验证结果关联、原始输出、退出码、环境、失败修复轮次、跳过测试、降低断言、伪造通过、不适用理由和提交验收条件。
- **验收测试**：覆盖 Demo/checklist 生成、逐条 AC 结论、阻塞和有条件通过、非需求负责人、AI 无法自行确认、验收版本记录、验收失效和退回开发。
- **收尾测试**：覆盖功能现状创建或更新、主需求与场景同步、索引同步、全部成功才 `DONE`、部分失败保留人工结论、事务恢复和不可安全恢复时不覆盖。
- **并发与写入测试**：覆盖同一对象并发锁冲突、残留锁诊断、显式清理、单文件原子替换、`PREPARED`/`COMMITTING`/`COMMITTED` 恢复和基线冲突。
- **索引测试**：覆盖三类索引生成、受管理区块指纹、人工修改确认、区块外内容保留、输入不变时稳定输出和索引失败不改变业务状态。
- **结构与性能测试**：覆盖缺文件、孤儿 Spec、失效引用、基线失效、验收收尾不完整，以及目标数据规模下的 lint、索引、状态查询和单次状态变更时间。
- **端到端试点**：在隔离真实小项目中安装标准 Skill，使用 Claude Code 完成需求、grilling、排期、PRD、批准、开发、验证、人工验收和收尾；保留状态历史、原始测试输出、版本和人工确认记录。
- **Prior art**：仓库目前没有实现代码、测试目录或既有测试 seam，因此没有可复用的自动化测试范式。测试矩阵以已确认的 SRS/FSR 验收方案和 HLD 的 CLI 外部契约为基准，后续实现应继续保持黑盒 workspace 测试边界。

## Out of Scope

- 完整的 `flow`、`discovery`、`definition`、`release`、`design` 和 `growth` Skill。
- 完整 G0 到 G4 关口、版本发布、上线清单、运营分析、A/B 实验和复盘体系。
- 没有 PRD 的缺陷快速通道。
- Web、数据库、独立后端、账号、登录、权限系统、真实身份认证和电子签名。
- MCP 服务、自定义 npm 安装器和独立升级器。
- Claude 或其他 Agent 专属 Hook、内部 API 和不可绕过的系统安全边界。
- Git commit、merge、push 自动化。
- macOS、Windows 和其他 Agent 的 P0 兼容认证。
- 让 AI 自动决定排期、PRD 批准、验收通过、需求合并或范围扩大。
- 以实时文件监听替代 lint、门禁和 CI。
- 用数据库或远程服务替代本地文件事实来源。
- 在本 spec 内实现实际业务功能；本 feature 实现的是研发流程工具本身。

## Further Notes

- 本 spec 综合已确认的 SRS、FSR 和 HLD；这些文档继续作为需求、可行性边界和架构依据，spec 不重新解释它们的全部条款。
- 当前仓库没有实现代码、测试目录或 ADR。实现应从 `flow-core` 的 CLI 外部契约、项目规则加载、原子写入和测试 fixture 开始，再接入各阶段 Skill。
- 本 spec 使用项目领域词汇：`Skill`、`flow-core`、`grilling`、人工确认、主需求、基线、收尾、功能现状和受管理区块。新增实现文档应继续使用这些术语，避免引入同义词。
- `ready-for-agent` 表示需求和测试 seam 已经足够明确，可以进入实现拆解；它不表示代码已经实现或 P0 已验收。
- P0 的完成条件是：自动化测试覆盖关键合法与违规路径；CLI 可脱离 Agent 执行关键确定性操作；Claude Code 隔离端到端主链路走通；所有人工决策、状态、版本、验证证据和收尾结果可追踪。
- 由于取消 Hook，流程治理无法阻止用户直接编辑文件。实现必须把这一限制体现在错误提示、lint、CI 和文档中，不得对外宣称拥有不可绕过的安全强制能力。
