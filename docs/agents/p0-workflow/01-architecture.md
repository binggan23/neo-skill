# 架构分工与设计理由

阅读条件：首次理解 P0，或为新能力决定落在哪一层。需求依据见 [SRS §2–5](../../srs.md)，架构依据见 [HLD §2–5](../../hld.md)。

## 四方协作

```text
用户提出意图、作决定
  ↓
neo-skill 路由 → project / requirements / prd / dev / acceptance
              （upstream-progress 可在任意时刻插入：只读，不改状态）
  ↓ 读取事实、grilling、生成候选、请求确认
flow-core CLI
  ↓ 校验、取锁、受控写入、记录历史、返回 JSON
本地项目文件
  ↑ 状态查询、门禁、lint、index、recover 再次读取
```

| 参与者 | 负责 | 交接依据 |
| --- | --- | --- |
| 人 | 补业务判断、确认共识与排期、提交评审、批准 PRD、确认验收 | 明确决定、申报身份、目标对象与必要版本 |
| Skill | 理解自然语言、查事实、组织 grilling、起草文档、解释错误与下一步 | 读取 CLI 结果后向人报告，不从对话措辞猜状态 |
| flow-core | 编号、规则、状态机、职责核对、hash、开发门禁、锁、事务、索引 | `success`、`artifacts`、`errors`、`next_actions` 与退出码 |
| 本地文件 | 保存可复查的正文、metadata、历史、原始证据和事务记录 | 路径、稳定 ID、版本、摘要及人工确认记录 |

人可以直接使用 CLI；业务校验应与 Skill 调用相同。`--actor` 是职责核对与审计，不证明真实身份。Skill 也无法从参数判断某个“确认”是否真的来自人，因此交互约束与 CLI 校验都要保留。

## 为什么这样分工

| 选择 | 解决的问题 | 后续版本要承担的代价 |
| --- | --- | --- |
| 自然语言入口 + 确定性 CLI | 推理结果不能可靠地充当状态机或批准记录 | 新命令需有明确前置条件、失败行为和 JSON 契约 |
| 一个 PRD 对一个主需求、一个功能 | 控制范围和验收责任；相关需求只作引用 | 跨功能需求需拆分或设计显式关联，不能隐式扩范围 |
| 本地 Markdown/YAML | 人与 Agent 都能审查，安装不需要独立后端 | 并发、部分写入、结构漂移需靠锁、事务、lint 处理 |
| 人工决定与机械推进分开 | 自动测试不能代替排期、批准和验收 | READY_FOR_ACCEPTANCE 可机械推进，ACCEPTED 仍需人工确认 |
| 基线绑定证据 | 避免拿旧需求、旧代码、旧测试结果验收新内容 | CR、代码变化、证据变化都需要重新验证有效性 |
| 索引只写受管理区块 | 自动生成总览，同时保留人工说明 | 必须检测区块内人工改动，确认后才能重新生成 |

“文件很长”不是重构结论。先看一次规则变化是否迫使多个调用方理解同一套顺序、状态和失败模式，再判断能否把这些知识集中在一个接口后面。

## 安装发布源与项目规则基线

- 安装资源：[`skills/neo-skill/runtime/`](../../../skills/neo-skill/runtime/)，随 Skill 分发 CLI、规则、模板。
- 项目基线：初始化目标项目中的 `.specify/rules/flow.yaml`、`.specify/templates/` 与 constitution。
- 运行时规则优先级由 [`rules.py`](../../../skills/neo-skill/runtime/flow_core/rules.py) 的 `load_rules` 定义。项目已有规则不等于安装包的当前默认规则。
- 升级设计需明确哪些内容只补缺、哪些需要展示计划并确认、旧项目如何兼容。不能把“安装更新成功”推导成“所有项目基线已迁移”。

## 产品边界

P0 实现需求到验收收尾；`flow/discovery/definition/release/design/growth` 的完整流程、G0–G4、身份认证、独立后端、无 PRD 快速通道均是后续候选。目录骨架出现了这些名字，不代表能力已实现。

Neo Skill 本身不自动执行 Git commit、merge、push。仓库研发中的 PR 与代码合并是工程交付动作；验收收尾的 COMMITTED 是文件事务状态。两种“提交”含义不同。
