# 后续版本的思考与交付方法

阅读条件：讨论新版本、重构、增加 Skill 或放宽治理边界。本页提供提问顺序和验证清单，不预先批准任何候选。需求来源仍是 [SRS §11](../../srs.md) 与真实使用反馈。

## 从一个可观察的问题开始

每个候选先回答：谁在什么操作上受阻？能给出输入、当前结果、期望结果吗？这个问题靠文档/配置能解决，还是需要改变行为？

记录格式：

```text
触发：哪个人/Skill/命令，在什么项目状态下做什么
事实：源码、CLI 结果、原始日志、历史文档的指针
期望：可观察结果与不应改变的现有行为
决策：谁需要决定；推荐答案及理由
假设/未决：哪些尚未验证，哪些依赖前一个决定
范围：本次做/不做；失效与恢复如何处理
验收：合法路径、违规路径、旧项目兼容性、失败恢复
```

AI 查事实，人决定产品取舍。先收敛 frontier，再形成 spec 和带阻塞关系的 tickets。不要让历史实现顺序或一张图的省略项自动变成新版本优先级。

## 新能力放在哪里

| 问题 | 首选落点 | 需要的证据 |
| --- | --- | --- |
| 只是问法、文档候选或人工提示不清 | 阶段 Skill 的交互设计 | 同一 CLI 行为下，用户能否更清楚地决定 |
| 同一事实被多个 Skill 各自判断 | flow-core 的公共规则/能力 | 一个外部契约覆盖所有调用者的合法与非法路径 |
| 新状态、职责、跳转、目录约定 | 声明规则 + 命令校验 + 项目基线升级 | 旧规则如何迁移、历史如何保留、异常如何拒绝 |
| 重复跨文件协调或恢复步骤 | 能隐藏该协调的模块接口 | 调用方需要知道的顺序减少，行为与故障测试仍成立 |
| 新安装布局、平台或 Agent | 安装资源与兼容性验证 | 隔离安装、路径搬移、资源发现和真实调用证据 |

行数只能帮助定位，不能证明模块浅。重构先列出调用方必须知道的顺序、配置、不变量、错误模式；确认新接口能隐藏这些知识，再决定拆/合，避免只把长文件搬成更多小文件。

## 候选与需要先回答的问题

| 候选 | 当前边界或证据 | 下一轮先问什么 |
| --- | --- | --- |
| ACCEPTED 后 CR 的闭环 | 当前可标失效，但终态无出边，再批准/恢复不完整 | 是创建新 PRD、新版本，还是允许终态重开？如何保留旧验收、撤销 CR 和重验？ |
| 验证可信度 | guard 为 Python 文本线索；外部结果可登记 | 支持哪些 runner/语言？哪些检查强制、哪些只能人工审查？证据由谁产生？ |
| release 与 G0–G4 | P0 只到已验收，没有上线状态 | 版本与功能验收如何关联？上线是否新人工关口？失败如何回退？ |
| discovery/definition/design/growth | 已有骨架，不代表对应 Skill 完整存在 | 真实项目缺哪种决定/产物？它阻塞了哪一步？能否先做一个切片？ |
| 更多 Agent / OS | P0 只记录 Linux 与 Claude Code 试点 | 安装目录、权限、路径编码、依赖与真实调用分别怎样认证？ |
| 并行与规模演进 | 本地文件 + 对象锁 + 收尾事务 | 锁粒度、跨对象顺序、索引一致性是否仍成立？增加并发会带来什么新竞争？ |
| 性能或模块重构 | 应以实际慢路径/修改扩散为依据 | 耗时在哪？改变接口后怎样证明行为不变与维护成本下降？ |

“加入数据库/服务端”“去掉人工确认”“AI 自动排期”等都改变既定边界。先形成新需求与 ADR 再实施，不能当作内部重构带入。

## 一项变更的影响清单

提 spec 前逐项注明影响或写“不影响 + 原因”：

1. REQ/PRD/SC/AC/CR 的 ID、路径、引用与历史。
2. Skill 交互、人工职责、确认点、CLI 参数与 JSON/退出码。
3. PRD hash 的锁定范围、开发引用、验证快照、验收有效性。
4. 功能现状、场景、索引、锁与事务恢复。
5. 已初始化项目的 `.specify/` 基线、模板和旧记录的升级策略。
6. 黑盒测试、安装模拟、端到端试点、外部调用与性能预算。

## 仓库工程交付

这里是开发 Neo Skill 的办法，不是产品内核自动执行的功能。

- 把任务分成有完成标准的切片，必要时用 spec + tickets 形成任务图；每个 implementer 独立 worktree，先建 CodeGraph 索引。探索约定见 [codegraph.md](../codegraph.md)。
- 同一 ticket/worktree 同时只有一个写入者；不能靠“没有新 commit”推断 agent 已停止。重启前确认终止、检查脏文件并保留有用产出。
- 静态检查与测试入口是 [`scripts/check.sh`](../../../scripts/check.sh)；CI 见 [ci.yml](../../../.github/workflows/ci.yml)。注意缺工具时本地脚本可能 SKIP，退出 0 不能证明缺席的检查已运行。
- 测试通过 CLI 边界验证行为；规模夹具的内部构造需由一致性测试约束。先跑相关文件，改动未变化且已绿时不反复全量重跑。
- 安装与发布验证包括 [`install-sim.sh`](../../../scripts/install-sim.sh)、[`pilot.sh`](../../../scripts/pilot.sh)。二者验证资源/确定性主链；外部 Claude 调用另行记录，不把排除/跳过写成通过。
- 使用 code-review 做 Standards/Spec 复核；有可执行 finding 派 fix，按根 [AGENTS.md](../../../AGENTS.md) 的轮次和升级约定处理。fix 的实际文件限制见 [定义](../../../.agents/agents/fix.md)，它限制 `skills/**`；runtime 也在该路径下，遇到冲突应指出并处理授权，不能擅自改写限制。
- ticket 状态与代码合入是两项交付。本仓库 issue 记在本地 Markdown（见 [tracker](../issue-tracker.md)）；代码变更先建立可审查分支/PR，列出证据，再按授权合并推送。事后 PR 只能留记录，不能替代合并前审查。

## 完成标准与维护

新版本需有可追溯的决定、合法/违规/恢复证据、旧基线兼容方案、安装与适用兼容性结果。测试数、历史 benchmark、图件自动校验回执都只证明对应版本与对应检查，不代表所有语义正确或所有平台兼容。

更改流程时同步本目录中受影响的章节和图件说明；不要复制整份命令 help 或规则文件。用源码路径 + 符号与需求编号指向事实来源，避免行号漂移。
