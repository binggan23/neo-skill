# AI 产品研发流程与 Skill 体系 FSR 可行性分析报告

- **文档类型**：FSR（Feasibility Study Report，可行性研究报告）
- **评估对象**：`AI产品研发流程与Skill体系.md`
- **结论**：**有条件可行，建议启动 P0 最小闭环**
- **评估日期**：2026-10-31

## 1. 执行摘要

该方案适合采用“标准 Skill + 声明式流程规则 + 独立执行内核 + 文件化产物”的方式落地。P0 应只验证“需求 → 人工排期 → PRD → 开发 → 人工验收”的主链路，不同时建设完整的 0→1 产品管理平台。

原方案总体流程、职责划分和文档体系具备可实施基础，但不能原样直接实施，需先完成以下调整：

1. **取消 Claude Code Hook**，改为 Agent 无关的受控 CLI、状态校验、结构检查及 CI 补强。
2. **采用 AI First 混合架构**：AI 负责理解、追问和内容生成，确定性内核负责编号、状态、hash 和校验。
3. **引入共享 grilling 协议**：提需求、制作 PRD 和其他人类决策场景采用设计树、逐轮追问、共识摘要和显式确认。
4. **补齐 P0 排期入口**：`requirements` 在需求对齐后询问 **“是否设置 xxx 需求排期”**，经用户明确同意并确认目标版本后才进入 `PLANNED`。
5. **限定兼容性承诺**：内核保持 Agent 无关，标准 Skill 尽量可移植，P0 仅以 Claude Code 做隔离的端到端实测，不宣称所有 Agent 已兼容。
6. **首期不走无 PRD 的缺陷快速通道**，所有正式开发必须绑定有效且已批准的 PRD。

在上述条件下，P0 的技术与实施风险可控。取消 Hook 后，流程约束属于**流程治理与质量保障**，不是不可绕过的安全边界；这是必须在验收和推广时明确接受的限制。

## 2. 目标与评估范围

### 2.1 目标

评估以下内容是否可落地，以及 P0 应如何收敛：

- 原文定义的目录、文档、编号和状态机；
- `flow-core`、阶段 Skill 和共享交互规范；
- PRD 批准、内容锁定、开发门禁和人工验收；
- Agent 无关的分发、执行和验证方式；
- 真实小项目的端到端试点。

### 2.2 已确认的关键决策

| 决策项 | 结论 |
| --- | --- |
| P0 范围 | 只做需求到验收的最小闭环 |
| 目录规范 | 完整采用原文目录，包括 `04-prds/`、`06-specs/adr/` 等 |
| Hook | 取消，不使用 Claude 或其他 Agent 专属 Hook |
| 技术形态 | 本地文件驱动，不建设 Web、数据库、权限平台或独立后端 |
| AI First | 声明式规则 + 结构化接口 + Python 参考实现 + 自然语言 Skill 入口 |
| 分发 | 采用标准 `SKILL.md`，首选 `npx skills@latest add binggan23/neo-skill`，参考 `mattpocock/skills` 的可复制、可组合 Skill 方式 |
| 实测 Agent | P0 仅实测 Claude Code；不恢复 Claude 专属绑定 |
| 人工控制 | 排期、PRD 批准、验收及其他人类决策均需显式确认 |
| 身份认证 | P0 记录操作人、时间、对象和 hash，不实现登录、电子签名或法律身份认证 |
| 缺陷通道 | P0 不实现无 PRD 的小 bug 快速通道 |

### 2.3 不在本期范围

- `flow`、`discovery`、`definition`、`release`、`design`、`growth` 的完整实现；
- G0～G4 的完整关口流程；
- 完整版本规划、上线发布、运营分析、A/B 实验；
- 无 PRD 的缺陷快速修复；
- Web 平台、多人权限系统、身份认证、数据库和独立后端；
- MCP 服务；未来可作为可选适配层；
- 所有现有及未来 Agent 的兼容认证。

### 3.2 原方案需要修正或补齐的地方

| 问题 | 影响 | 处理方案 |
| --- | --- | --- |
| P0 没有完整 `release`，但需求必须先进入 `PLANNED` | 主链路卡在 PRD 之前 | 在 `requirements` 增加人工排期确认 |
| Hook 绑定 Claude，且不能覆盖所有操作路径 | 跨 Agent 和强制约束不成立 | 受控 CLI + lint + CI；明确非安全边界 |

| 人工批准只有状态要求，缺少交互提醒 | AI 可能擅自推进 | 统一“共识摘要 + 轮到你确认 + 显式确认”协议 |
| 非开发 Skill 的追问方式不统一 | 易漏问、一次问太多或询问已知事实 | 共享 grilling 设计树与逐轮 frontier 机制 |
| 小 bug 可不写 PRD，与 P0 全量门禁冲突 | 规则不一致 | P0 所有正式开发统一走 PRD，快速通道后置 |
| “全 Agent 兼容”缺少可验证定义 | 容易形成过度承诺 | 通用内核 + 标准 Skill + 指定 Agent 实测 |

## 4. 推荐方案

### 4.1 AI First 混合架构

```text
用户自然语言
    ↓
阶段 Skill：理解意图、检索事实、grilling、生成内容、请求确认
    ↓
flow-core：声明式规则、确定性操作、状态与完整性校验
    ↓
结构化结果：success / artifacts / errors / next_actions
    ↓
项目文件：需求、PRD、Spec、代码、测试、验收与索引
```

AI First 不意味着把状态与审批交给模型自由维护，而是：

- 用户通过自然语言启动流程，无需记忆脚本命令；
- Skill 按当前上下文决定需要追问和调用的能力；
- 状态机、目录和门禁规则声明式配置，避免散落在提示词与代码中；
- 每次内核调用返回结构化结果，使 Agent 能理解失败原因并恢复；
- 内核可脱离 Agent 手工执行，便于测试、审计和跨 Agent 复用；
- AI 不替代人类做排期、批准、验收或关口决策。

### 4.2 `flow-core` 职责

`flow-core` 是所有 Skill 共用的流程引擎，负责：

- 初始化项目骨架，重复执行安全且不覆盖已有文件；
- 分配 REQ、PRD、SC、DEC、CR、ADR 等编号；
- 创建需求条目、PRD 目录和标准 metadata；
- 校验状态跳转，记录操作人、时间与历史；
- 计算、锁定和验证 PRD 内容 hash；
- 检查开发前置条件及 PRD/Spec 引用；
- 检查必需文件、目录与 ID 一致性、孤儿 Spec、失效引用及验收收尾；
- 生成 `backlog.md`、`feature-map.md` 和 PRD 索引；
- 提供声明式规则、文档模板和机器可读执行结果。

它不负责判断需求价值、撰写需求或 PRD 正文、技术设计、自动批准或自动验收。

### 4.3 Setup 入口

不增加独立 setup Skill。由 `project` 的初始化能力承担类似 `setup-matt-pocock-skills` 的入口职责：

1. 检查仓库当前状态；
2. 创建原文规定的项目目录、模板和 `.specify/`；
3. 生成或更新项目 `AGENTS.md` 中的流程约定；
4. 保留已有文件，不静默覆盖；
5. 调用 `flow-core` 完成确定性初始化。

### 4.4 共享 grilling 与人工确认协议

参考 `mattpocock/skills` 的 `grilling` 设计，将以下机制作为 `flow-core` 共享交互规范，由相关 Skill 引用：

1. **设计树**：将需求拆为有依赖关系的决策。
2. **逐轮 frontier**：每轮只问前置条件已经明确的问题，并给出推荐答案。
3. **事实与决策分离**：AI 自行查询代码和文档，不让用户回答可查证事实。
4. **共识摘要**：列出已确认决策、假设和未决问题。
5. **显式最终确认**：正式生成、批准或状态推进前，由人确认共享理解。

提需求与 PRD 制作必须采用该协议。其他非开发 Skill 在涉及范围、排期、审批、验收或关口决策时也采用；状态查询、索引生成等机械操作不强行追问。

人工确认提示必须明确说明当前轮到用户决策，例如：

> 以上信息已对齐。**请你确认是否批准 PRD-001；只有你明确确认后，我才会记录批准。**

P0 的确认记录包含操作人、时间、确认对象和相关 hash。该记录用于防止 AI 擅自批准，不构成身份认证或电子签名。

### 4.5 需求排期

`requirements` 完成需求对齐后必须询问：

> **是否设置 xxx 需求排期**

处理规则：

- 用户不同意：需求保持 `TRIAGED`；
- 用户同意但目标版本未确认：继续询问，不修改状态；
- 用户明确同意并确认目标版本：记录人工排期结果，再执行 `TRIAGED → PLANNED`；
- AI 不得自行决定优先级或目标版本。

该能力只补齐 P0 主链路，不提前实现完整 `release` Skill。

### 4.6 开发门禁与取消 Hook 后的约束

正式开发必须通过“开发 PRD-xxx”一类入口显式绑定 PRD。`dev` 启动时：

1. 检查 PRD 存在且状态允许开发；
2. 检查批准记录与内容 hash；
3. 绑定后续 Spec、Plan、Tasks、验证报告和代码工作；
4. 检查失败则停止，不生成 Spec、不修改正式代码；
5. 发现需求问题时停止并提问，不自行扩大范围；
6. 测试完成后可进入 `READY_FOR_ACCEPTANCE`，但不能自行改为 `ACCEPTED`。

通用 lint 与 CI 再检查 Spec/PRD 引用、状态和必需产物。该方案无法阻止人或 Agent 绕过 Skill 直接编辑文件，因此属于流程治理，不是绝对安全边界。

### 4.7 分发与 Agent 兼容策略

参考 `mattpocock/skills`：

- 使用标准 `SKILL.md` 组织可复制、可修改、可组合的 Skill；
- 首选通过 `skills.sh` 通用安装器分发，P0 验证 Claude Code 的标准 Skill 加载；
- 项目约定写入 `AGENTS.md`，确定性能力放入独立 CLI；
- 不依赖 Claude Hook、Claude 内部 API 或特定模型行为。

推荐安装命令：

```bash
# 交互选择目标 Agent 和需要安装的 Skill
npx skills@latest add binggan23/neo-skill

# 或明确安装到 Claude Code
npx skills@latest add binggan23/neo-skill -a claude
```

安装完成后，用户通过 `project` Skill 初始化业务项目。`npx skills add` 只负责安装 Skill 及其资源，项目初始化才负责创建 `00-management/` 至 `09-growth/`、`.specify/` 和项目级 `AGENTS.md` 等内容。P0 不单独建设 npm 包或自定义 npm 安装器，除非试点证明通用安装器无法满足需求。

`flow-core` 的 CLI、声明式规则和模板必须随 Skill 一起安装，并通过安装目录内的相对路径调用，不能依赖开发机器的源码仓库路径。

兼容性承诺分层：

| 层级 | 承诺 |
| --- | --- |
| CLI、声明式规则、模板、Git/CI | Agent 无关，可独立执行 |
| 标准 Skill | 面向支持 Agent Skills 规范的 Agent 提供可移植基线 |
| 追问、工具调用、联网、子 Agent 等 | 取决于具体 Agent 和模型能力 |
| 不支持文件、命令或 Skill 的助手 | 只能使用手工 CLI，不保证完整自动流程 |
| 未经实测的 Agent | 不宣称已完成兼容验证 |

P0 仅认证 Claude Code。其他 Agent 后续按相同测试矩阵补测。

## 5. P0 交付范围

| 模块 | P0 交付 |
| --- | --- |
| `flow-core` | 项目骨架、模板、编号、需求/PRD 创建、状态机、hash、开发门禁、结构检查、索引、结构化结果 |
| `project` | 仅项目初始化、目录与 `AGENTS.md` 配置；不做完整立项、周报和 G0～G4 |
| `requirements` | grilling、结构化需求、去重分类、共识确认、人工排期 |
| `prd` | grilling、场景化 PRD、AC、自审、评审、人工批准、hash 锁定、CR 变更 |
| `dev` | PRD 绑定与门禁、Spec/Plan/Tasks、开发、测试、验证报告、提交人工验收 |
| `acceptance` | 按 AC 验收、人工结论、功能现状/需求/场景状态同步 |
| 工程保障 | 声明式规则、独立 CLI、自动化测试、CI、Claude Code 隔离试点、安装与使用文档 |

P0 的试点输入是已经完成立项和产品定义的小项目，不要求从空白想法覆盖完整 0→1。

## 6. 技术与实施可行性

### 6.1 技术可行性：高

所需能力主要是本地文件处理、YAML/JSON、hash、状态机、模板渲染、命令执行和测试，没有必须依赖的复杂基础设施。Python 3.11+ 适合作为参考实现；优先使用标准库，仅引入必要的 YAML 解析与测试依赖并锁定版本。

Python 只是内核实现语言，不决定产品是否 AI First。AI First 主要由自然语言入口、声明式规则、结构化接口和可恢复交互实现。

### 6.2 流程可行性：中高

原文的主流程和职责划分较完整。补齐人工排期、grilling 和确认协议后，P0 能形成闭环。主要风险是规则过多导致使用成本升高，应通过共享模板、默认推荐和逐轮追问控制交互负担。

### 6.3 跨 Agent 可行性：中

通用内核和标准 Skill 具备可移植基础，但不同 Agent 的发现机制、工具权限、模型行为和交互能力不同。P0 只实测 Claude Code 可控；跨 Agent 推广必须逐个验证，不能仅因文件格式相同就认定兼容。

### 6.4 治理可行性：中

受控命令、状态历史、hash、lint 和 CI 能显著提高一致性，并防止 AI 在正常 Skill 流程中绕过审批。但没有实时 Hook、仓库写权限控制或服务端检查时，无法阻止刻意绕过。P0 可接受此限制，团队推广前需重新评估 Git 服务端检查或权限控制。

### 6.5 试点可行性：高

已有 Claude Code 环境，且测试可在临时目录或独立 worktree 中进行。试点无需改变当前 Agent、全局 Skill、模型配置或凭据，也不要求安装其他 Agent。

## 7. 测试与验收方案

### 7.1 `flow-core` 自动化测试

| 测试项 | 必测用例 |
| --- | --- |
| 初始化 | 空项目创建完整目录；重复执行不覆盖；异常目录返回结构化错误 |
| 编号与创建 | 编号递增不复用；目录、ID、slug、metadata 一致 |
| 状态机 | 合法流转成功；非法跳转拒绝；操作人、时间和历史完整 |
| PRD hash | 批准时锁定；篡改后失败；CR 重新批准后恢复有效 |
| 门禁 | 只有绑定且 hash 有效、状态允许的 PRD 才能开发 |
| 结构检查 | 缺文件、孤儿 Spec、失效引用、验收后未更新现状均可发现 |
| 索引 | 三类索引内容正确，重复生成稳定 |
| AI 友好接口 | 成功和失败均返回状态、产物、错误和建议下一步 |

### 7.2 Skill 交互测试

- **`project`**：初始化完整、已有文件不覆盖、不替人做关口决策。
- **`requirements`**：按设计树逐轮追问；AI 自查事实；摘要确认；必须询问 **“是否设置 xxx 需求排期”**；不同意则保持 `TRIAGED`，明确同意并确认版本后才进入 `PLANNED`。
- **`prd`**：基于需求、现状与术语表追问；覆盖做/不做、异常场景和可测试 AC；正式生成前确认；AI 不能批准；批准后修改必须走 CR。
- **`dev`**：必须绑定 PRD；未批准或 hash 失效时停止；生成 Spec/Plan/Tasks；保留原始测试输出；不自行扩大范围或验收。
- **`acceptance`**：按 AC 核对；明确提醒用户确认；AI 不能判定通过；通过后同步现状、需求、场景；不通过则记录问题并退回开发。

### 7.3 违规与异常测试

以下路径必须被拒绝或停止：

1. 未排期需求直接制作正式 PRD；
2. `DRAFT` PRD 直接进入开发；
3. 批准后篡改 PRD 再进入开发；
4. AI 自行批准 PRD；
5. 非法状态跳转，例如 `DRAFT → DEVELOPING`；
6. 跳过测试直接提交验收；
7. AI 自行确认验收通过；
8. 验收后不更新功能现状文档；
9. Spec 引用不存在或不匹配的 PRD；
10. 未绑定 PRD 直接启动正式开发。

### 7.4 端到端主链路

在隔离的真实小项目中使用 Claude Code 完成：

```text
提出需求
→ grilling 对齐
→ 用户确认并排期
→ grilling 制作 PRD
→ 人工批准并锁定 hash
→ 绑定 PRD 开发
→ 自动测试与验证报告
→ 提交人工验收
→ 用户明确确认通过
→ 更新功能现状与索引
```

必须保留文档、状态历史、原始测试输出和人工确认记录。

### 7.5 安装、CI 与环境隔离

- 使用临时目录或独立 worktree，不修改当前全局配置和已有项目；
- 通过 `npx skills@latest add binggan23/neo-skill -a claude` 安装后，Claude Code 能发现并调用标准 Skill；
- `flow-core` 可脱离 Agent 手工运行；
- CI 能运行自动化测试和结构检查，违规样例必须失败；
- 不使用 Claude Hook，不调用 Claude 专属内部 API。

## 8. 工作量与路线建议

在没有团队人数、Agent 使用熟练度和试点项目复杂度数据时，不给出虚假的人日或预算。按相对工作量评估：

| 工作包 | 相对工作量 | 说明 |
| --- | --- | --- |
| 声明式规则与 `flow-core` | 大 | P0 核心，需优先保证状态与一致性 |
| `requirements` / `prd` | 中大 | 内容模板之外，还需可靠 grilling 与确认交互 |
| `dev` / `acceptance` | 中大 | 涉及真实代码、测试证据和跨产物同步 |
| `project` 初始化与模板 | 中 | 规则明确，主要是完整性与幂等性 |
| 测试、CI、隔离试点 | 中大 | 是可行性成立的必要条件，不能省略 |
| 安装与使用文档 | 小中 | 包括手工 CLI 和 Claude Code 两种路径 |

推荐顺序：

1. 冻结 P0 规则、状态机和元数据；
2. 实现 `flow-core` 与自动化测试；
3. 实现 `project` 初始化、`requirements` 和人工排期；
4. 实现 `prd`、批准/hash/CR；
5. 实现 `dev` 和 `acceptance`；
6. 接入 CI，在隔离环境运行 Claude Code 端到端试点；
7. 根据试点结果调整模板与交互，再决定 P1。

## 9. 主要风险与应对

| 风险 | 等级 | 应对 |
| --- | --- | --- |
| 无 Hook 后绕过流程 | 高 | 受控入口、lint、CI、审计记录；明确非安全边界 |
| 状态与文档不一致 | 高 | 仅通过内核改状态；事务化或失败回滚；结构检查 |
| AI 擅自批准或验收 | 高 | 共享确认协议；人工状态必须带显式确认与操作人 |
| 追问过多导致流程繁重 | 中高 | 设计树逐轮提问、推荐默认值、简单需求自动收敛 |
| Skill 与内核规则重复漂移 | 中高 | 声明式单一事实来源，Skill 只引用规则 |
| 跨 Agent 行为差异 | 中 | 只认证已实测 Agent；保持 CLI 可独立运行 |
| 测试证据伪造或失真 | 高 | 保存原始输出、退出码和关联对象；人工抽查 |
| 初始化覆盖已有内容 | 中高 | 幂等、冲突报告、默认不覆盖、隔离试点 |
| P0 范围膨胀 | 中高 | 明确排除项；完整 0→1 和平台化后置 |
| 本地身份记录被误当成认证 | 中 | 文档明确能力边界，平台化时再实现身份与权限 |

## 10. Go/No-Go 条件

### 启动 P0 的条件

- 接受 P0 最小闭环和排除项；
- 接受取消 Hook 后的治理边界；
- 接受 Claude Code 单 Agent 实测，不承诺全 Agent 兼容；
- 能提供一个已完成立项和产品定义的真实小项目；
- 能安排真实用户完成排期、PRD 批准和人工验收。

### P0 通过条件

- 第 7 节五层测试全部有结果，核心违规路径均能被拒绝或停止；
- 真实需求端到端主链路完整走通；
- 所有状态和人工决策可追溯；
- 原始测试证据与验收材料齐全；
- Claude Code 隔离试点不污染现有开发环境；
- CLI 可脱离 Agent 执行关键确定性操作。

### 应暂停或重新设计的情况

- 需求方要求不可绕过的安全强制，却不接受仓库权限或服务端检查；
- 要求 P0 同时覆盖完整 0→1、所有 Agent 和平台化能力；
- 无法提供真实试点或人工验收人；
- 试点显示追问和文档成本明显高于实际研发收益，且无法通过裁剪改善。

## 11. 最终结论

**建议 Go，但仅限定义清晰的 P0。**

推荐方案能够把原文从“流程与提示词规范”转化为可执行、可验证、可追溯的 AI 协作研发闭环。其可行性依赖于确定性内核与 AI 交互的合理分工，而不是增加更多提示词或依赖某一 Agent 的 Hook。

P0 成功后再进入 P1：补全 `flow`、`discovery`、`definition`、`release`、G0～G4 和版本管理；P2 再实现 `design`、`growth`、运营分析及更多 Agent 的兼容验证。是否引入 MCP、Git 服务端强制检查或身份权限平台，应由试点暴露的真实问题驱动，而非提前建设。
