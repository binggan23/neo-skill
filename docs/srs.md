# Neo Skill SRS 软件需求规格说明书

- **文档版本**：v0.1.1
- **产品范围**：P0 最小研发闭环 + v0.1.1 可组合 Skills 与上游进度查询
- **需求基线**：`AI产品研发流程与Skill体系.md`、`docs/fsr.md` 及已确认的 grilling 决策
- **目标读者**：产品、AI Agent、开发、测试与验收人员

## 1. 引言

### 1.1 目的

本文定义 Neo Skill P0 与 v0.1.1 范围内可实现、可验证的需求，覆盖项目初始化、需求管理、人工排期、PRD、Spec 驱动开发、人工验收、`flow-core`、可组合 Skills 和上游进度查询。本文重点规定系统行为、业务规则、异常处理和验收口径。

### 1.2 产品目标

以标准 Skill 和自然语言交互为入口，以独立 CLI 为确定性内核，打通以下闭环：

```text
需求 → grilling 对齐 → 人工排期 → PRD → 人工批准
     → Spec/开发/测试 → 人工验收 → 功能现状与索引同步
```

Skills 按职责拆分为可组合的入口/编排能力与可复用的基础能力；项目接入可绑定上游及进度资料，进度查询以远端资料为依据，并将本地 Git 元数据提示与远端进度分开报告。

系统必须遵循“PRD 驱动、AI 执行、人工把关”，不得由 AI 自行决定排期、批准 PRD 或判定验收通过。

### 1.3 需求优先级

| 标识 | 含义 | 验收约束 |
| --- | --- | --- |
| MUST | 当前版本必须实现 | 未满足则当前版本验收不通过 |
| SHOULD | 当前版本应当实现 | 不阻塞当前版本验收，但需记录未完成原因 |
| COULD | 可选增强 | 不作为当前版本验收条件 |

除非另有说明，本文编号需求均为 MUST。

### 1.4 术语

| 术语 | 定义 |
| --- | --- |
| Skill | 使用标准 `SKILL.md` 描述的自然语言流程入口 |
| `flow-core` | 提供确定性流程操作和校验的独立 CLI 及声明式规则 |
| grilling | 按设计树逐轮追问、由 AI 查事实、由人做决策的对齐方式 |
| 主需求 | 一个 PRD 直接实现并在验收后完结的需求 |
| 基线 | 当前 PRD 内容、hash、代码版本及验证证据形成的可追踪组合 |
| 人工确认 | 用户明确表达决定、申报身份并经 `team.md` 职责核对后的操作 |

## 2. 范围与边界

### 2.1 P0 范围

- `flow-core`：目录、模板、编号、状态、hash、门禁、lint、索引、结构化结果；
- `project`：项目初始化、团队配置、项目约定；
- `requirements`：需求草稿、grilling、去重分类、确认与人工排期；
- `prd`：PRD、AC、自审、提交评审、人工批准、hash、CR；
- `dev`：PRD 绑定、Spec/Plan/Tasks、开发、测试、验证报告、提交验收；
- `acceptance`：Demo 材料、AC 清单、人工结论、验收及收尾同步；
- 安装、CLI、自动化测试、CI 和当前 Linux 环境的 Claude Code 试点。

### 2.2 非目标

- 完整 `flow`、`discovery`、`definition`、`release`、`design`、`growth`；
- 完整 G0～G4、版本发布和运营能力；
- 无 PRD 的缺陷快速修复；
- Web、数据库、独立后端、账号、登录、权限系统、电子签名；
- MCP 服务和自定义 npm 安装器；
- macOS、Windows 或其他 Agent 的 P0 认证；
- 不可绕过的系统安全边界。

### 2.3 运行与治理边界

- 所有正式产物由本地文件保存，目录采用原始方案规定；
- 所有 Agent 共用 CLI、规则和模板；P0 仅实测 Claude Code；
- 取消 Agent 专属 Hook；受控命令、lint 和 CI 属于流程治理，不能阻止刻意直接编辑文件；
- 人工 CLI 与 Agent 流程具有同等业务校验，但均不构成身份认证；
- 本地文件驱动不代表内容不发送给模型服务商，团队须遵守公司的模型与数据政策。

### 2.4 v0.1.1 范围

v0.1.1 在保留 P0 研发闭环行为的基础上，增加可组合 Skills 的职责分层、项目上游绑定和远端进度查询（SRS-FR-090～095）。通用工程能力与 Neo 产品阶段能力继续作为同一 Skills 仓库中的独立 Skills；入口/编排能力与可复用基础能力按职责区分，不得把工程技能描述成 `flow-core` 自动执行的产品能力。

## 3. 用户、职责与交互原则

### 3.1 人员与职责

系统不要求用户在流程发起时声明角色，也不实现角色权限系统。`team.md` 保存人员标识、姓名及职责映射；同一人员可承担多个职责。

| 职责 | P0 关键行为 |
| --- | --- |
| 需求提出者 | 提交需求、回答业务问题、参与评审 |
| 需求负责人 | 确认需求对齐、决定排期、提交和批准 PRD、验收 |
| 开发/测试（可选） | 技术评审、处理复杂问题、审查验证证据 |
| 项目负责人 | 初始化团队配置；P0 不执行完整关口决策 |
| AI Agent | 查事实、grilling、生成产物、执行测试、提醒确认、调用受控命令 |

### 3.2 身份确认

**SRS-BR-001**：普通起草、检索和 grilling 不要求身份输入。排期、提交评审、批准、验收等人工决策时，系统必须提醒“现在需要你确认”，并询问“你是谁”。

**SRS-BR-002**：系统必须将申报身份与 `team.md` 匹配，并核对该人员是否承担当前职责。身份不存在或职责不匹配时，只保留待确认状态，不修改业务状态。

**SRS-BR-003**：人工确认记录至少包含人员标识、时间、决策对象、决定及相关 hash 或版本。申报身份仅用于职责核对和审计，不代表已验证真实身份。

### 3.3 共享 grilling 协议

**SRS-FR-001**：`requirements`、`prd` 及其他需要人类决策的非开发流程必须：

1. 将问题组织为有依赖关系的设计树；
2. 每轮只询问前置条件已明确的 frontier 决策；
3. 由 AI 自行查询代码和文档，不询问可查证事实；
4. 为问题提供推荐答案，并允许用户修正；
5. 汇总已确认决策、假设和未决问题；
6. 在正式生成或状态推进前取得显式确认。

**SRS-BR-004**：状态查询、索引生成等机械操作不强制 grilling。简单需求的设计树可按实际决策收敛，但不得省略必要的最终确认。

## 4. 总体业务流程

```text
project 初始化目录、team.md、constitution.md
    ↓
requirements 创建 NEW 草稿 → grilling → 用户确认 → TRIAGED
    ↓ 询问“是否设置 xxx 需求排期”
需求负责人确认目标版本 → PLANNED
    ↓
prd 创建 DRAFT → grilling/自审 → 提交评审 → IN_REVIEW
    ↓ 需求负责人明确批准
APPROVED + 内容 hash
    ↓
dev 显式绑定 PRD → DEVELOPING → Spec/Plan/Tasks/代码/测试
    ↓ 全部适用验证通过
READY_FOR_ACCEPTANCE + 代码版本与验证证据
    ↓
acceptance 生成 checklist → 用户验收 → 需求负责人明确确认通过
    ↓
ACCEPTED → 功能现状/主需求/场景/索引同步完成
```

**SRS-BR-005**：P0 所有正式开发必须关联有效 PRD，不提供无 PRD 的缺陷快速通道。

**SRS-BR-006**：自动测试通过、Demo 启动、生成验收报告或代码合并均不得单独触发 `ACCEPTED` 或 `DONE`。

## 5. 功能需求

### 5.1 安装、升级与环境检查

**SRS-FR-010**：系统必须支持以下安装方式：

```bash
npx skills@latest add binggan23/neo-skill
npx skills@latest add binggan23/neo-skill -a claude
```

**SRS-FR-011**：Skill 包必须包含其调用所需的 `flow-core`、声明式规则和模板；运行时使用安装目录内的相对路径，不得依赖开发机器的源码仓库路径。

**SRS-FR-012**：系统必须提供 `doctor` 命令，检查 Python 3.11+、Node.js 18+、Skill 资源和 `flow-core` 可用性；缺失时输出修复提示，不得自动安装全局软件或修改用户配置。

**SRS-FR-013**：升级说明必须且只需指导用户执行 `npx skills@latest update`，不实现自定义升级器或额外升级后检查要求。

### 5.2 `project`：初始化

**SRS-FR-020**：初始化必须按原始方案创建完整目录骨架和必要模板，即使对应阶段尚未实现。不得伪造 charter、调研结论或业务数据。

**SRS-FR-021**：用户可在初始化时显式裁剪原始方案允许省略的非核心目录；默认不裁剪。charter、MVP scope、PRD 状态与门禁、人工验收相关能力不得关闭。

**SRS-FR-022**：初始化必须收集并展示团队摘要，经用户确认后生成 `team.md`，至少包含需求负责人和项目负责人。缺少有效团队配置时可保留目录骨架，但项目为“未配置完成”，不得排期或批准。

**SRS-FR-023**：初始化必须提供 `.specify/constitution.md` 默认模板，并要求用户在首次正式开发前确认技术、安全、测试和架构约束。

**SRS-FR-024**：初始化只补齐缺失内容，不覆盖已有 `README.md`、`AGENTS.md`、业务文档或代码。冲突时先展示变更计划，经用户确认后写入；`AGENTS.md` 仅更新受管理的 Neo Skill 区块。

**SRS-FR-025**：初始化必须可重复执行；已满足条件的步骤不得重复创建或覆盖内容。

### 5.3 `requirements`：需求与排期

**SRS-FR-030**：grilling 开始时可创建 `NEW` 需求草稿，保存当前进展。草稿至少逐步收集背景、用户、问题、场景、期望结果和来源。

**SRS-FR-031**：系统必须与已有需求及功能现状比对，提示重复或关联关系；AI 不得在无用户确认时删除或合并需求。

**SRS-FR-032**：需求必须支持新功能、优化、缺陷、技术债分类，并标注所属模块。优先级可采用 RICE 或 MoSCoW，并记录理由。

**SRS-FR-033**：完成 grilling 后必须展示共识摘要；只有用户确认后才将需求从 `NEW` 转为 `TRIAGED`。关键信息不完整时不得进入 `PLANNED`。

**SRS-FR-034**：需求对齐后必须询问 **“是否设置 xxx 需求排期”**：

- 用户拒绝：保持 `TRIAGED`；
- 用户同意但未确认目标版本：继续询问，不修改状态；
- 需求负责人明确同意并确认版本：记录决定并转为 `PLANNED`。

**SRS-FR-035**：需求进入 `IN_PRD` 前，需求负责人可确认取消或调整排期；进入 `IN_PRD` 后必须通过 PRD 变更或重新评审处理，不得无记录改期或取消。

### 5.4 `prd`：PRD、批准与变更

**SRS-FR-040**：只能从 `PLANNED` 主需求创建正式 PRD。一个 PRD 只能有一个主需求、覆盖一个功能；其他需求只能作为相关需求引用。

**SRS-FR-041**：创建 PRD 后，主需求转为 `IN_PRD`，PRD 初始状态为 `DRAFT`。PRD 必须关联模块、功能、场景、目标版本和主需求。

**SRS-FR-042**：PRD 必须按原始模板包含背景目标、范围、现状与变化、场景、AC、非功能需求、数据需求、依赖风险和待确认问题。

**SRS-FR-043**：一个 PRD 最多 8 个场景，超过必须拆分；每个场景至少一条可测试的 Given/When/Then AC。

**SRS-FR-044**：新功能没有功能现状文档时，PRD 必须明确“新功能，无现状”，不得因此阻塞；验收后创建现状文档。

**SRS-FR-045**：AI 必须执行章节完整性、范围、AC 可测试性、模糊词、术语和冲突自审，并输出问题清单。

**SRS-FR-046**：grilling 和自审完成后，系统必须提醒用户提交评审并询问身份；确认后记录提交人，将 PRD 从 `DRAFT` 转为 `IN_REVIEW`。提交评审与批准是两个独立确认点。

**SRS-FR-047**：评审完成后，系统必须再次提醒批准并询问身份。只有需求负责人明确同意，才能转为 `APPROVED`、记录批准信息并锁定 hash。

**SRS-FR-048**：批准时的锁定范围包括 `prd.md`、metadata 中的需求范围字段及存在的 `test-cases.md`。评审记录、状态历史和 CR 文件作为追加记录，不参与正文 hash。

**SRS-FR-049**：已批准 PRD 的正文或锁定字段需要变化时必须创建 CR。CR 至少包含内容、原因、对 Spec/Tasks/测试/设计/版本的影响、版本变化和审批信息。

**SRS-FR-050**：开发中创建 CR 后，PRD 必须退回 `IN_REVIEW`；已有 Spec、代码和测试保留但标记“基线失效”，重新批准前不得继续正式开发。

**SRS-FR-051**：CR 重新批准必须递增 PRD 版本并生成新 hash。旧批准和旧验收结论保留为历史，但对当前内容不再有效。

### 5.5 `dev`：开发、验证与提交验收

**SRS-FR-060**：正式开发必须从“开发 PRD-xxx”等入口显式绑定 PRD。未绑定、PRD 不存在、状态不允许、hash 失效或 constitution 未确认时，必须停止且不生成 Spec、不修改正式代码。

**SRS-FR-061**：门禁通过后，PRD 转为 `DEVELOPING`，并按相同模块和 PRD 路径生成 `spec.md`、`plan.md`、`tasks.md`。

**SRS-FR-062**：AI 必须检查 Spec、Tasks 和代码变更是否超出 PRD。疑似超范围时停止并提示，不得自动修改 PRD；只能由人通过 CR 或明确澄清裁决。

**SRS-FR-063**：发现 PRD 问题时必须停止相关开发并提示 CR，不得自行修改需求、验收标准或扩大范围。

**SRS-FR-064**：开发必须执行适用的单元测试、集成测试和静态检查，生成 `verification.md`，将每条 AC 关联到验证结果，并保存原始输出、退出码和执行环境。

**SRS-FR-065**：测试失败时 AI 可自动修复，但不得删除用例、降低断言、跳过测试或修改 AC 来制造通过。默认最多连续修复 3 轮，项目可在 constitution 中调整；达到上限或需求不明确时必须请人介入。

**SRS-FR-066**：只有所有适用验证项通过才能提交验收。未执行或阻塞项不得写成通过；确实不适用时必须在 Spec/PRD 中记录理由，不得以环境限制自动豁免。

**SRS-FR-067**：满足提交条件后，AI 可自动将 PRD 转为 `READY_FOR_ACCEPTANCE` 并提醒用户验收，无需额外人工批准。

**SRS-FR-068**：提交验收时必须记录当前 Git commit；非 Git 项目记录源代码和测试文件内容摘要。该版本必须与验证报告和验收清单关联。

### 5.6 `acceptance`：人工验收与收尾

**SRS-FR-070**：系统必须准备 Demo 访问与操作材料，并按 AC 生成 `checklist.md`。每项 AC 必须具有通过、不通过或阻塞结论及相应证据；AI 可建议结论，但不能代替人确认。

**SRS-FR-071**：只有全部 AC 通过，系统才可提醒用户确认“验收通过”。系统必须询问身份并核对需求负责人，只有其明确确认后才由受控命令将 PRD 从 `READY_FOR_ACCEPTANCE` 转为 `ACCEPTED`。

**SRS-FR-072**：验收报告必须记录验收人、时间、PRD hash、代码 commit 或内容摘要、逐项 AC 结论和遗留问题。

**SRS-FR-073**：“有条件通过”不得转为 `ACCEPTED`。系统必须记录遗留问题，并由用户选择退回开发或重新验收；不通过必须退回 `DEVELOPING`。

**SRS-FR-074**：PRD 内容或 hash 变化、验收范围内代码变化、验证报告被替换时，已提交或已有验收结论必须失效，并重新执行验收。

**SRS-FR-075**：验收确认后必须更新功能现状、主需求、场景状态和生成索引。首次验收的新功能必须创建功能现状文档。

**SRS-FR-076**：只有 PRD 已 `ACCEPTED`、功能现状更新成功、场景状态和索引同步成功后，主需求才能转为 `DONE`。代码合并或测试通过不能单独完成需求。

**SRS-FR-077**：验收收尾必须作为一致性操作处理。任一步失败时保留人工验收结论和错误，显示“已确认通过，收尾未完成”，提供重试或恢复入口，不得报告全部完成。

### 5.7 `flow-core`：公共内核

**SRS-FR-080**：系统必须提供声明式目录、编号、状态机、门禁和模板规则，作为 Skill 与 CLI 的单一事实来源。

**SRS-FR-081**：系统必须分配 REQ、PRD、SC、DEC、CR、ADR 等编号；编号只增不复用，废弃编号保留，slug 创建后不变。

**SRS-FR-082**：状态只能通过受控命令变更；命令必须校验合法跳转，人工状态必须带身份、时间和确认记录。

**SRS-FR-083**：系统必须提供 PRD hash 计算、锁定和验证，以及开发门禁、PRD/Spec 引用检查。

**SRS-FR-084**：`lint` 必须检查必需文件、目录与 ID 一致性、孤儿 Spec、失效引用、基线失效及验收后现状同步。

**SRS-FR-085**：系统必须生成 `backlog.md`、`feature-map.md` 和 PRD 索引。生成文件使用受管理区块；检测到区块内人工修改时提示重新生成，经用户确认后覆盖生成区块，保留区块外说明。

**SRS-FR-086**：CLI 必须同时提供人类可读输出和 `--json`。结构化结果至少包含 `success`、`artifacts`、`errors`、`next_actions`；错误包含错误码、原因、对象和建议下一步。

**SRS-FR-087**：CLI 失败必须返回非零退出码，不得修改业务状态或留下半写入正式产物。

**SRS-FR-088**：系统必须通过锁文件或等效机制拒绝多个流程同时修改同一需求或 PRD。命令中断后不得留下半写入文件，并允许安全重试或给出明确恢复提示。

**SRS-FR-089**：用户必须可通过 Agent 或直接使用 CLI 完成排期、批准和验收；两种入口执行相同校验。CLI 必须要求显式确认参数和 `--actor`，不得默认代替人确认。

### 5.8 可组合 Skills 与上游进度查询（v0.1.1）

**SRS-FR-090**：Skill 集合必须按职责拆分能力。需要编排多步工作流的入口 Skill 与承载单一、可复用工作纪律的基础 Skill 应保持独立；入口可调用基础 Skill，但不得把多个无关流程堆入单一 Skill。具体 Skill 名称与分组属于实现设计，不由本需求预先限定。

**SRS-FR-091**：项目接入流程必须询问用户是否为当前项目绑定上游项目，并收集上游 URL/标识及用于判断进度的远端资料来源。用户确认后，将信息记录到项目级 `AGENTS.md` 或等价 Agent 指引；没有该类指引时，记录到 `README.md` 的明确小节。不得覆盖文档中无关内容。

**SRS-FR-092**：用户可调用进度查询 Skill，查询已绑定上游的远端资料并据此报告当前进度。报告必须区分已发布事实与仍在进行中的远端事项，注明查阅来源；无法访问或证据不足时明确报告不确定性，不得把本地工作区内容推断成上游进度。

**SRS-FR-093**：进度查询可读取项目级 `AGENTS.md`、等价 Agent 指引或 `README.md` 中的上游绑定配置，以取得 URL/标识和进度来源；这些配置只用于定位远端，不作为进度事实。查询可读取本地 Git 元数据（如分支、工作区 dirty 状态、本地领先/落后远端提交数）以提示尚未提交或推送的变更；这些信息必须作为本地提醒单列，不得并入远端进度结论。不得读取本地代码、业务文件或其他正文来推断上游进度。

**SRS-FR-094**：当前项目没有上游绑定文档时，进度查询必须向用户询问上游 URL 和进度资料来源；用户可仅为本次查询临时提供，不要求自动写回项目文档。

**SRS-FR-095**：项目接入写入上游绑定信息前，必须展示拟记录的 URL/标识、进度来源和目标文档位置并取得用户确认；保留目标文档中其他内容。用户不提供或不确认时可继续其他初始化步骤，但必须明确提示进度查询尚未配置。

## 6. 数据对象与状态规则

### 6.1 核心对象

| 对象 | 必备关联 |
| --- | --- |
| REQ | ID、slug、模块、分类、来源、状态、目标版本、关联 PRD |
| PRD | ID、slug、模块、功能、场景、主需求、版本、状态、hash、人员与历史 |
| SC/AC | 模块与场景编号、至少一条可测试 AC |
| CR | 所属 PRD、原因、内容、影响、版本、审批与历史 |
| Spec/Plan/Tasks | 模块、PRD、基线版本、验证关联 |
| Verification | PRD、代码版本、AC 结果、原始输出、退出码、环境 |
| Acceptance | PRD hash、代码版本、逐项 AC、结论、验收人、时间、收尾状态 |
| Team | 人员标识、姓名、职责映射 |

### 6.2 REQ 状态机

```text
NEW → TRIAGED → PLANNED → IN_PRD → DONE
  └──── 可保留草稿；TRIAGED/PLANNED 可 DEFERRED 或 REJECTED
```

- `NEW → TRIAGED`： grilling 摘要经用户确认；
- `TRIAGED → PLANNED`：需求负责人确认排期与目标版本；
- `PLANNED → IN_PRD`：正式 PRD 创建；
- `IN_PRD → DONE`：PRD 验收及全部收尾完成；
- 排期调整按 SRS-FR-035 执行。

### 6.3 PRD 状态机

```text
DRAFT → IN_REVIEW → APPROVED → DEVELOPING
  ↑          ↓                     ↓
  └── CHANGES_REQUESTED       READY_FOR_ACCEPTANCE
       ↑                           ↓       │
       └──────── CR ───────── ACCEPTED   不通过
                                  ↓
                            P0 不包含 RELEASED
```

- `CHANGES_REQUESTED` 返回修改后必须重新提交评审；
- CR 可从已批准或开发相关状态触发 `IN_REVIEW`，并使旧基线失效；
- `APPROVED` 和 `ACCEPTED` 必须人工确认；
- `READY_FOR_ACCEPTANCE` 可由 AI 在满足证据条件后自动提交；
- `REJECTED`、`SUPERSEDED` 保留为受控旁支，编号和历史不得删除。

### 6.4 场景状态

P0 使用“待规划 → 已规划 → 开发中 → 已验收”。“已上线”和“已下线”属于后续发布范围，不得在 P0 以验收代替发布。

## 7. 业务硬规则

| 编号 | 规则 |
| --- | --- |
| SRS-BR-010 | 未排期需求不得制作正式 PRD |
| SRS-BR-011 | 未绑定有效已批准 PRD 不得正式开发 |
| SRS-BR-012 | 已批准内容不得直接修改，必须走 CR 并重新批准 |
| SRS-BR-013 | AI 不得自行排期、批准 PRD 或判定验收通过 |
| SRS-BR-014 | AI 不得伪造测试、调研、用户、身份或验收数据 |
| SRS-BR-015 | 不得跳过适用验证或以降低质量门槛制造通过 |
| SRS-BR-016 | 基线变化后旧批准或验收不得自动沿用 |
| SRS-BR-017 | 未更新功能现状和索引不得将主需求标为完成 |
| SRS-BR-018 | 必须遵守项目 constitution 的安全、测试和架构约束 |
| SRS-BR-019 | 废弃对象保留编号和历史，不得通过删除掩盖变更 |

## 8. 非功能需求

| 编号 | 优先级 | 需求与验收口径 |
| --- | --- | --- |
| SRS-NFR-001 | MUST | P0 仅在当前 Linux 环境认证；其他操作系统不作为本期验收项 |
| SRS-NFR-002 | MUST | Python 3.11+、Node.js 18+；优先标准库，必要依赖必须声明并锁定 |
| SRS-NFR-003 | MUST | Skill 默认中文交互，用户可切换语言；目录、ID、slug、状态值为英文；文件使用 UTF-8，支持中文正文和姓名 |
| SRS-NFR-004 | MUST | 1,000 条需求或 200 个 PRD 数据集上，常规 `lint`、索引和状态查询在常规开发机 10 秒内完成；单次状态变更 2 秒内完成，不含 AI 生成和项目测试 |
| SRS-NFR-005 | MUST | 文件写入必须原子化或具备等效恢复能力，并发冲突不得损坏已有文件 |
| SRS-NFR-006 | MUST | 所有人工决定和状态历史可追踪，时间采用带时区的标准格式 |
| SRS-NFR-007 | MUST | 日志、错误、CI 输出不得包含凭据；系统不得主动上传项目文件或依赖独立后端 |
| SRS-NFR-008 | MUST | 测试证据必须保留原始输出和退出码，不只保存 AI 摘要 |
| SRS-NFR-009 | SHOULD | 相同输入和规则的索引生成结果应稳定，无业务变化时不产生随机差异 |

## 9. 异常、恢复与限制

- 身份或职责不匹配：保留待确认，不改变状态；
- 缺少团队配置：允许目录骨架存在，禁止人工排期和批准；
- 缺少 constitution 确认：禁止正式开发；
- 门禁或 hash 失败：停止开发，不生成新 Spec、不修改正式代码；
- CR 导致基线失效：保留已有工作，禁止继续开发直至重新批准；
- 测试失败：按修复上限处理，不得掩盖失败；
- 验收不通过或阻塞：不得 `ACCEPTED`，记录原因并退回或等待；
- 收尾部分失败：保留确认结论，明确未完成并可重试；
- 命令中断或并发冲突：不留下半写入产物，拒绝冲突或提供恢复；
- 直接绕过 Skill 编辑文件：lint/CI 尽可能发现，但 P0 不承诺实时阻止；
- 非 Git 项目：使用内容摘要建立验收版本关联。

## 10. 验收与追踪

### 10.1 P0 端到端验收

在当前 Linux 的隔离目录或 worktree 中，通过标准安装命令安装并在 Claude Code 中完成：

1. 初始化目录、确认 `team.md` 和 constitution；
2. 创建真实需求并完成 grilling、确认和人工排期；
3. 制作 PRD，分别完成提交评审和需求负责人批准；
4. 绑定 PRD 开发，生成 Spec/Plan/Tasks 并完成验证；
5. 自动提交人工验收，由需求负责人明确确认通过；
6. 验证 `ACCEPTED`、功能现状、主需求 `DONE`、场景和索引一致；
7. 保存完整状态历史、原始测试输出、版本和人工确认记录。

### 10.2 必测违规路径

| 验证场景 | 关联需求 | 预期 |
| --- | --- | --- |
| 未排期直接创建 PRD | FR-040 / BR-010 | 拒绝 |
| 未绑定或 DRAFT PRD 开发 | FR-060 / BR-011 | 停止且无正式写入 |
| 篡改批准后 PRD | FR-048 / BR-012 | hash 失效，禁止开发 |
| AI 自行批准或验收 | BR-013 | 状态不改变 |
| 非法状态跳转 | FR-082 | 拒绝并记录错误 |
| 跳过或伪造测试 | FR-064～066 | 不得提交验收 |
| 有条件通过标记 ACCEPTED | FR-073 | 拒绝 |
| 基线变化沿用旧验收 | FR-074 | 验收失效并重新验收 |
| 收尾未完成需求 DONE | FR-076～077 | 不得 DONE，提示恢复 |
| 并发修改同一对象 | FR-088 | 拒绝冲突且文件完整 |

### 10.3 需求覆盖

验收必须覆盖当前版本范围内的全部 MUST 需求。至少建立以下追踪：

| 主链路 | 需求组 |
| --- | --- |
| 安装与诊断 | FR-001～FR-013、NFR-002 |
| 初始化与团队 | FR-020～FR-025 |
| 需求与排期 | FR-030～FR-035 |
| PRD 与 CR | FR-040～FR-051 |
| 开发与验证 | FR-060～FR-068 |
| 人工验收与同步 | FR-070～FR-077 |
| v0.1.1 Skills 与上游进度 | FR-090～FR-095 |
| P0 公共内核与恢复 | FR-080～FR-089 |
| 质量与治理 | 全部适用 BR、NFR |

## 11. 后续版本候选

以下为非 v0.1.1 需求，不影响 v0.1.1 验收：

- 完整 0→1、G0～G4 和版本发布；
- `flow` 状态路由、discovery、definition、release、design、growth；
- 无 PRD 的受控缺陷快速通道；
- 更多 Agent、macOS、Windows 的认证；
- MCP、Git 服务端强制检查、账号权限与身份认证；
- 根据真实试点决定裁剪、性能和交互优化。
